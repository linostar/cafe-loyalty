# Cafe Loyalty

A cash-first loyalty tool for independent cafés in Tripoli, Lebanon. Customers get a phone-number loyalty card in Apple Wallet, Google Wallet or a web card; baristas add stamps from an offline-capable counter app; owners see busy and quiet hours, win back lapsed regulars and run quiet-hour offers that never discount below a margin floor.

Customers and owners see it as **Loyalty Everywhere** (loyaltyeverywhere.com), a name defined once (`PRODUCT_NAME`, packages/shared/src/brand.ts).

## Requirements

- Node.js 22 (see `.nvmrc`)
- pnpm 11.24, enabled through Corepack: `corepack enable`
- Docker with Compose, for the local PostgreSQL database
- ShellCheck, which `pnpm lint` runs on the deploy scripts (`brew install shellcheck`; GitHub's Ubuntu runners have it)

## Setup

```sh
cp .env.example .env        # then set a local POSTGRES_PASSWORD
pnpm install
pnpm exec playwright install chromium
pnpm db:up                  # starts PostgreSQL on 127.0.0.1 and waits until it is healthy
pnpm db:bootstrap           # creates the roles, the application database and its schemas
pnpm db:migrate             # applies the migrations
pnpm --filter @cafe-loyalty/server build
pnpm --filter @cafe-loyalty/server create-invite --cafe-name "Test Café"   # prints a single-use owner signup link
```

`PUBLIC_URL` is this server's own public address, used in café signup QR codes and recovery links. `COUNTER_URL` is the counter app's address (no path; `http://localhost:5174` locally, https in production): pairing QR codes open its `/pair` page. To try the dashboard against the API locally, set `DASHBOARD_API_PROXY=http://127.0.0.1:3000` in `.env`, then run the server and the dashboard dev servers (see Commands) and open `http://localhost:5173`; `COUNTER_API_PROXY` does the same for the counter app (`http://localhost:5174`, started with `--port 5174`). The session cookie is `Secure`, which Chrome and Firefox allow on `http://localhost` (Safari does not; use Chrome or Firefox locally, and `localhost`, not `127.0.0.1`, as `DASHBOARD_URL`). Without SMTP credentials locally, leave `SMTP_USER` and `SMTP_PASSWORD` unset and point `SMTP_HOST`/`SMTP_PORT` at a mail catcher such as Mailpit; the server checks the SMTP connection at startup and logs an error if it fails.

## Design system

- **One source.** `packages/ui` holds the design tokens (`src/tokens.css`: colours, type, spacing, radius, shadow, motion), the base styles every front end shares (`src/base.css`: elements, controls, messages, cards, checkbox labels), the dashboard and counter components (`src/app.css`: badges, pills, row lists and actions, the brand, top bar and footer, empty states, visually hidden text), the customer pages' layer (`src/customer.css`), the font list (`src/fonts.css`) and the logo (`assets/logo.svg`). The dashboard and the counter import the CSS through Vite (`main.tsx`) and add only their own layout (`src/styles.css`); the server inlines tokens, base and customer styles (without comments, and without app.css) into each customer page, so the page's CSP still allows its one stylesheet by hash. Apps use the tokens and never set colour values of their own.
- **The look.** Warm café: a cream page, white cards with a soft shadow, espresso text and top bar (the passes' colour), and one copper accent for primary actions, links, the current page and focus. A form's submit button is the primary action; other buttons are outlined, and `.danger` marks what cannot be undone.
- **Font.** IBM Plex Sans Arabic (SIL OFL 1.1, from `@fontsource/ibm-plex-sans-arabic`): regular, semibold and bold, Arabic and Latin in one family, each subset with its `unicode-range` and `font-display: swap`. The apps bundle it; the server serves the same files at `/assets/fonts/<file>` (and the logo at `/assets/logo.svg`), so the customer pages' CSP adds only `font-src 'self'` and `img-src 'self'`. The counter's service worker keeps the font, logo and icons offline.
- **Checks.** `packages/ui/src/tokens.test.ts` computes the contrast of every colour pair the styles draw (WCAG AA: 4.5:1 for text, 3:1 for control borders and focus), and fails on a colour token it does not check. `styles.test.ts` fails on any physical-direction property (`margin-left`, `left:`, `width:`, `text-align: right`, four-value shorthands) in any front end's stylesheet: use logical ones (`margin-inline-start`, `inset-inline-start`, `inline-size`, `text-align: end`), so right-to-left pages need no styles of their own.
- **Adding a style.** A component the customer pages and an app both use goes in `base.css`, one only the dashboard and counter use in `app.css` (it stays out of every customer page); one app's layout goes in its own `styles.css`. Use the tokens; a new colour is a new token, added to the contrast test's pairs. Nothing sticks to the top of the viewport over the page, since a focused control could hide under it (the screen specs walk the focus back up each page to check). Keep the accessible names, roles and labels the tests read, and wrap text rather than splitting a sentence a test matches.
- **Brand files.** The logo is hand-written SVG. The counter's PWA icons are made from it: `rsvg-convert -w 192 -h 192 packages/ui/assets/logo.svg -o packages/ui/assets/icon-192.png` (and 512); the counter's build adds them with its web app manifest. Page titles and the theme colour come from `PRODUCT_NAME` and the tokens (`brandHtml` in each app's vite.config.ts).
- **Screenshots.** `e2e/dashboard/screens.spec.ts`, `e2e/dashboard/customer-screens.spec.ts` and `e2e/counter/screens.spec.ts` capture every screen at 1440, 1024 and 390 px with fake data and attach them to the Playwright report (`test-results/` locally). They compare no pixels; the counter's checks that a landscape tablet keeps the order's total and Record visit button in view.

## Languages and accessibility

- **Arabic and English** (AC 41). Every screen works in both, right to left in Arabic. The customer pages pick the language from `?lang=` or the browser (server-rendered, `customer-html.ts`); the dashboard and the counter from the viewer's last choice (the language button in the top bar, kept in the browser's `localStorage` as `cl_lang`) or else the browser's languages (`langFromPreferences`, packages/shared: the first Arabic or English one, else Arabic), and set `<html lang dir>` to match. Arabic screens use Latin digits, dollar amounts as `$3.50` and the Arabic names of order types, rewards and campaigns; inputs accept Arabic-Indic digits too.
- **Text.** Each app file writes its text in English as `t("…")` and lists its Arabic in a catalog at the top of the file (`useT`, `apps/*/src/i18n.tsx`); `t` takes only listed text, so a string without its Arabic does not compile. Values go in `{name}` placeholders, isolated in Arabic so Latin names, emails and numbers keep their order; counts use `plural` (Arabic's six forms). The API speaks English: every message it can send (errors, field issues, the shared schemas' messages) is in `API_MESSAGES_AR` (`packages/shared/src/api-messages.ts`) with its Arabic, `ApiError` and the schemas take only listed messages (`apiText`, or `apiMessage` to fill placeholders), and the apps show them through `useApiText` (`localiseApiMessage`). A message the catalog does not know, such as a newer server's, is shown in English rather than lost.
- **Accessibility.** Labels on every control, keyboard operation with visible focus, focus moved to what changed, and every error says what happened and what to do next (AC 42). `eslint-plugin-jsx-a11y` (strict) lints both apps, and the Playwright specs check each screen in both languages at 360 px for horizontal overflow and for controls without an accessible name (`e2e/a11y.ts`).

## Database

PostgreSQL 18. Everything lives in schema `app`; migration history is in `meta.schema_migrations`.

- **Roles.** `cl_owner` owns every object and is used only by migrations; `cl_app` holds the runtime privileges. Neither can log in. Each environment has two login roles: a migrator that is a member of `cl_owner`, and an app role that is a member of `cl_app` only. No role has superuser or BYPASSRLS. Bootstrap sets passwords as SCRAM verifiers, so plaintext never reaches the server or its logs. The group roles are cluster-wide, so staging and production each run their own PostgreSQL server.
- **Tenant isolation.** Every table has forced row-level security that shows and accepts only the rows of the café set for the current transaction. Code reaches the database only through `withCafe(db, cafeId, work)`, with a café id taken from the authenticated session, device or job, never from request input; the one exception is the operator's admin routes (see Results and plans), which take the café from the route, after checking the operator's session and that the café exists, because an operator acts on every café. Before any café is known (signing in, opening an invite or reset link, checking a session cookie), `withLookup(db, key, work)` runs a transaction (read-only unless asked otherwise) that shows only the rows matching what the caller holds: an owner's or operator's email, a token or secret hash, a device key id; the café id it finds is then used with `withCafe`. The one place a café id is created rather than looked up is café creation, by the operator: the `create-invite` command generates it, and the admin screen's New café form makes it in the browser (so a form sent again creates the café once).
- **Job queue.** pg-boss, in schema `pgboss`, created by migration `0007` (never by pg-boss itself): the app role reads and writes jobs and calls pg-boss's functions but cannot create or alter anything, and pg-boss runs with its schema migration, reindexing and stored statistics off. The worker refuses to start on a pg-boss schema version other than its library's; the server (which only sends jobs) then runs without the queue, recording stamps but pushing no pass updates, so a release rolled back past a pg-boss upgrade still serves. A pg-boss upgrade that changes the version needs a migration made from `getMigrationPlans`. Every hour the worker removes expired owner sessions (including idle ones), reset links, invites, device tokens, pairing codes, card recovery links and operator sessions (including idle ones) through `purge_expired_credentials()`, which runs as the owner role and sees only expired rows. A failed run is logged and retried; every job-queue statement is limited to 5 seconds, and pg-boss's warnings are logged.
- **Migrations.** Plain SQL files in `packages/db/migrations`, numbered `0001_...sql`, each starting with `-- migration: expand` (adds only, safe for the previous release) or `-- migration: contract` plus `-- requires-deployed: <commit>` (removes or renames, only once the deployed release no longer uses it). Applied migrations are never edited; the runner refuses a changed file and refuses to run an older release on a newer database. Deploys run it in expand mode (see Deploying).

## Owner accounts

- **Invite only.** The operator creates the café on the admin screen (New café, or New signup link on a café for a fresh link or another owner; the link is shown once, with a copy button) or with `create-invite`, which prints the same kind of single-use signup link (`/signup#invite=…`, valid 7 days). The link is a secret until used: send it to the owner directly, never in a shared channel or a ticket. The owner opens it, chooses an email and a password (at least 10 characters) and is signed in. Tokens in links sit in the URL fragment, which browsers never send to a server.
- **Passwords** are hashed with argon2id (19 MiB, 2 passes). Sign-in answers a wrong password and an unknown email identically.
- **Sessions** are server-side rows keyed by the SHA-256 hash of a random 256-bit token sent as a `__Host-` cookie (`HttpOnly`, `Secure`, `SameSite=Strict`). They end after 7 days idle or 30 days in all. Signing out, changing the password and resetting it end every session of the owner. Every write must carry a JSON body (`{}` when empty), so a cross-site page, even on a sibling subdomain, cannot post to it.
- **Password reset** emails a single-use link (`/reset-password#token=…`) valid 30 minutes; only the newest link works, and the email says so. Completing a reset lifts any sign-in lockout on the account. Passwords are compared in Unicode NFKC form and their length is counted in characters. Sign-in emails must be in Latin letters. The reply is the same, and sent before any lookup, whether or not the email has an account.
- **Rate limits** (per server process, reset on restart; an IPv6 client counts by its /64 network): sign-in 30 attempts per 15 minutes per IP, and failed attempts only: 10 per 15 minutes per account and IP, 100 per hour per account; reset requests 5 per hour per IP and 3 per email; reset completion 10 per 15 minutes per IP; signup 10 per hour per IP; password change 10 per 15 minutes per owner; setting PINs (adding a barista or changing a PIN) 30 per hour per owner; pairing codes 20 per hour per owner; failed pairings 10 and failed token renewals 30 per 15 minutes per IP (failures only, because counters share the café's Wi-Fi address with customers); renewals 30 per hour per device; syncs 240 per hour per device. In production the server refuses to start unless `TRUST_PROXY_HOPS` is set (1 behind Caddy) and `DASHBOARD_URL` is https.

## Café setup, staff and devices

- **Café.** The owner sets the café's name, the loyalty program (stamps for a reward, reward name in Arabic and English) and order types (names in both languages, USD price and cost in cents, stamps earned, on sale or not). Adding an order type or changing a price or cost bumps the café's catalog version. Every change is in the audit log.
- **Staff.** The owner adds each barista with a PIN of 6 to 12 digits (no repeated digit or straight run) and tells it to them. The server keeps only a salted PBKDF2-SHA256 hash (600,000 iterations), which paired phones receive to check PINs offline. A 6-digit PIN's hash can be cracked offline in minutes by whoever holds a paired phone, so the phone's lockout is what protects PINs: staff should not reuse a PIN from elsewhere, and longer PINs are safer. Removing a barista keeps their record for the history.
- **Devices.** The owner creates a single-use pairing code (12 characters, `ABCD-EFGH-JKMN`, valid 10 minutes, deleted after 5 wrong tries) shown as text and as a QR that opens the counter app's `/pair` page. Pairing registers the phone's P-256 public key and issues an access token valid 1 hour; the phone renews it by signing with its key. A phone that has not renewed for 7 days must pair again. Pairing again with a new code keeps the phone's device id (it proves its old key), so what it queued still syncs; from then on only the new key renews. A removed phone is told so (`DEVICE_REVOKED`) on its next request; until its current token expires it can still hand over its queue. Changing or resetting the owner's password cancels their open pairing codes.
- **Access.** Every API route declares who may call it: the owner (session cookie), a paired device (`Authorization: Bearer`), the operator (their own cookie, on `/api/admin` routes) or anyone; the server refuses to start if a route declares nothing. Owner routes answer 403 to a device token, and operator routes to an owner session or a device token.

## Counter app and sync

- **Pairing and baristas.** The counter opens at `/pair` from the dashboard's QR (or a typed code), makes a non-extractable WebCrypto key and keeps it, the access token, the baristas' PIN hashes and its queue in IndexedDB. A barista picks their name and enters their PIN, checked on the phone; they stay signed in until someone taps Switch barista. Five wrong PINs in a row lock that barista out on that phone for 30 seconds, doubling with each further wrong PIN up to an hour; the lockout survives reloads and is reported to the owner's audit log at the next sync.
- **Offline queue.** Everything the counter records is an event signed with the device key (device, key, staff and event ids, per-device sequence, schema version, time) and kept in IndexedDB until the server answers it for good. The counter syncs on start, when it comes back online and every 30 seconds while anything waits, at most 100 events per request.
- **Sync** (`POST /api/device/sync`) answers every event on its own, by index: applied, duplicate, rejected or retry_later, with a code. The device and café come from the token, never the event; the event's key must belong to that device and its signature must verify; `occurredAt` may be at most 30 days old; an event up to a day ahead of the server's clock (a phone clock running fast) waits as retry_later once it is more than 5 minutes ahead, and further ahead is refused. A verified event is recorded once in a ledger (unique per café, device and event id): sent again it is a duplicate, and with other content under the same id it is an idempotency conflict. Unknown types or versions answer retry_later, so a counter newer than the server keeps them. The counter drops an event only on applied, duplicate or rejected, and lists rejected ones on screen until cleared. Visits become stamps as they are recorded (see Stamping and rewards).
- **Review queue.** Actions from a removed phone (or signed by a key it had when removed) and from removed baristas are neither applied nor dropped (PIN lockout reports, which change nothing, are audited at once and say where they came from): the owner accepts or discards them on the dashboard's Review page, a page of 50 at a time. A removed phone's sync answer says so (`deviceRevoked`), and the phone unpairs at once.
- **Pairing again.** The proof from the old key covers the new code and the new key, so it works once. A phone still holding another café's identity is refused (`PAIRED_ELSEWHERE`, the code stays usable): the counter warns how many items would be lost and starts over as a new device only when someone confirms (at once when nothing waits). Tokens are stored with the key they were issued for, so a renewal that finishes after the phone paired again is dropped; renewals take one Web Lock across tabs, and every tab reloads its view when another changes the stored data.
- **Builds.** Every counter request carries `X-Counter-Built-At`. The API serves new actions only to counter builds made at most 14 days before its own release (`BUILT_AT`) and answers 426 otherwise; pairing, token renewal and sync work from any build, so an old counter always drains its queue. The service worker keeps the app usable offline and installs an update only once the queue is empty and nobody is typing; the status bar always shows the connection, what waits to be sent and the build.

## Stamping and rewards

- **Visits.** A signed-in barista adds what was ordered from the menu (the order types on sale, loaded with the baristas and kept for offline use) and identifies the card: by scanning its QR with the phone's camera (read on the phone, checked offline to be this café's), or by typing the customer's mobile number. The visit is queued and synced like any event, with each item's price, cost and catalog version as the counter saw them: the server stores them and never re-prices from today's catalog.
- **Stamps.** A visit earns the sum of its items' stamps (an order type's stamps times the quantity; items that earn none add nothing). It adds no stamps, but still counts as a visit, when the card got stamps within 30 minutes of the visit's time, in either order (a database exclusion constraint enforces this), or when the counter phone has added 300 stamps that day in the café's time zone (each phone has its own cap). Every stamp is audit-logged with the device and the barista, against the visit (`visit.stamped`) and never the card; rewards likewise (`reward.redeemed`).
- **Which card.** A QR must be genuine (signed), of this café and of the card's current epoch (`CARD_REPLACED` after a recovery). A phone number finds the card only through this café's cards, and only once that card has been scanned at a counter (`PHONE_NOT_CONFIRMED` before), because numbers are not verified. A scan proves who holds the card, not whose number it is: once a second card here signs up with the same number, the linked card is never stamped by number again (`PHONE_DISPUTED`), only by its QR, so someone who signed up first with another person's number cannot collect the stamps that person asks for. Refusals (`CARD_NOT_FOUND`, `CARD_REPLACED`, `PHONE_NOT_CONFIRMED`, `PHONE_DISPUTED`, `UNKNOWN_ORDER_TYPE`) are kept in the ledger, so a resend gets the same answer, and appear in the counter's error list. A held visit is applied, by its own time, only when the owner accepts it: one from a removed phone or barista, or one that reached the server more than two days after it happened (its time is the phone's to set and decides the cooldown and the daily cap, so backdated visits never stamp unseen). Accepting one says when it still added no stamps (cooldown, daily cap or a deleted card). The ledger keeps an HMAC of each event (keyed with the pepper), never a plain hash, which the stored visit would let anyone with the database reverse into the phone number.
- **Rewards** are online only: the barista scans the card, and the server takes the program's stamps in one atomic step, recorded once per redemption id. The counter keeps an unconfirmed redemption in IndexedDB and must try it again (same id, so it gets the first answer) before giving another, even after a reload or an update; it shows when that redemption started, so the barista knows which customer it was for. A build past the support window still gets the answer to a redemption it already sent. Offline, the counter says rewards need a connection.
- **Deleting a card** keeps its visits and redemptions for the café's numbers, with no link to the card.
- **Busy and quiet hours.** The dashboard home shows member visits (every visit recorded with a card, held and discarded ones excepted) of the last 4 weeks by weekday and hour, counted afresh on each load and reloaded hourly while the page stays open (`GET /api/cafe/visit-hours`). Each visit counts in the hour it happened (`occurredAt`) in the café's time zone (`cafes.time_zone`, Asia/Beirut), bucketed by PostgreSQL alone, so a late sync lands in its own hour and daylight-saving changeovers follow the time zone database; a held late visit counts once the owner accepts it.

## Quiet-hour campaigns

- **Minimum margin.** On the Café page the owner sets a minimum margin as a whole percentage over cost (0 by default: never below cost). A discounted price must stay at or above cost × (100 + margin) / 100, rounded up to the cent.
- **Campaigns** (dashboard, Campaigns page; `GET`/`POST /api/campaigns`, `POST /api/campaigns/:id/end`): weekdays and a local start and end time within one day, in the café's time zone; percent off (rounded down to the cent, in the café's favour) or a fixed amount off each unit; and the order types on sale it covers. A campaign is refused if its discount takes any of them below the margin floor (the dashboard previews each one's discounted price against its floor), keeps the café's margin from when it was made, and is never edited: the owner ends it and makes a new one. At most 20 run at once; the dashboard lists them and the 20 most recently ended.
- **At the counter.** The device catalog carries the running campaigns and the café's time zone; counters refresh it every 5 minutes while online. A visit's line gets the largest discount of a campaign running at that moment that covers its order type and keeps its floor, priced on screen at most 30 seconds before (the menu is priced again every 30 seconds) and recorded as priced, at that moment, so the recorded total is the one the barista charged. Visits are sent as `visit.recorded` version 2, whose lines carry `campaignId` and `unitDiscountCents` (version 1 is still accepted, as undiscounted lines).
- **Checked again at sync.** The server re-checks every discounted line against the campaign as it stood at the visit's time: made by then (allowing 5 minutes for a counter clock running behind) and not ended (or ended less than 10 minutes before, while counters catch up), running at the visit's local weekday and minute (read by PostgreSQL in the café's time zone), covering the order type, giving exactly the campaign's discount on the line's price, and keeping the campaign's margin floor on the line's cost. Otherwise the visit is held for the owner (Review page, "with a discount its campaign did not allow"): the customer paid the discounted price, so the owner accepts it (stamps added, discount kept on record) or discards it. A visit held for another reason (late, or from a removed phone or barista) still records that its discount failed (`visits.discount_refused`), and the Review page says so. A line naming a campaign this café does not have is refused (`CAMPAIGN_REFUSED`). Visit lines keep their campaign and discount. Price and cost are the counter's (never re-priced, AC 32), so this check catches a counter that misapplies a campaign, not one that misstates its catalog.
- **Announced on passes.** Every 5 minutes the worker announces each campaign whose window is open, with at least 15 minutes of it left, to the cards opted in to offers (`announceCampaigns`, apps/worker/src/offers.ts; the café ids come from `campaigns_to_announce`, which returns ids only): once per campaign and card, and to a card at most once a day in the café's time zone (`campaign_announcements`), 500 cards per campaign per run. An opted-in card's passes show its latest announced offer while that campaign runs: on Apple, an Offer field on the front ("Afternoon · 20% off", or "None right now") with the days, hours and order types on the back; on Google, a text module. The announcement is the only update that notifies, at most once a day per card (AC 14): the Apple field has a `changeMessage` only on the day the offer was announced (to a card opted in by then), and the first Google write after an announcement, that day, adds one `TEXT_AND_NOTIFY` message, to a pass saved before the announcement and only when the card's Apple pass is on no device (recorded on the pass before the write, so a retry never notifies twice; a failed notifying write is logged as a lost notification). An announcement, a campaign's end and opting in or out mark the card's passes changed in the database and queue their updates in the same transaction.

## Win-back offers

- **Lapsed cards.** Every hour, for each café whose local time is between 10:00 and 20:00 (new offers never go out at night), the worker records each card that lapsed (`runWinBack`, apps/worker/src/win-back.ts; the café ids come from `cafes_for_win_back`, which returns ids only): member visits (held and discarded ones aside) on at least 3 days, and the time since the last one longer than twice the median gap between those days, and at least 14 days. Several visits on one day count once. A lapse is recorded once per card and last visit (`card_lapses`), 500 per café per run; only cards last seen more than 14 days ago and not yet recorded are measured.
- **The offer** (dashboard, Café page; `PUT /api/cafe/win-back`): percent or amount off each item of the next visit, or none, and a cool-down from 14 to 365 days (30 by default). A card still lapsed (no member visit since) gets it as soon as the café has one, the card is opted in to offers and it got none within the cool-down, whether that holds when the lapse is recorded or on a later run. The offer keeps the café's terms and minimum margin of that moment, the ones its passes show, and lasts 14 days. It shows on the card's passes like a campaign ("Welcome back · 15% off", with its last day) and notifies under the same one-a-day cap: a card told of a campaign today gets it on a later run, and no campaign is announced to a card given a win-back offer today, or while that offer is open, so it stays on the passes until used or expired. The worker closes expired offers every hour, at any time of day, and turning the offer off closes the open ones; either way they leave the passes. Expiry, recording lapses and giving offers each run in their own transaction; only giving offers holds the café's row. The shared cap lives in the worker: while a worker from before Step 13 runs (a rollback), its campaign announcer does not see win-back offers, so a card given one that day can also be told of a campaign, which then shows over the offer until the next announcement or the offer's expiry.
- **At the counter.** The device catalog lists the open offers, by card and with their own terms. When the barista scans a card that has one, the counter offers "This card has a win-back offer, 15% off: apply it"; each line then gets the larger of its campaign's discount and the offer's, never below its margin floor, and the counter says when the offer takes nothing off the order. A card typed in by phone number cannot be matched offline, so it gets no win-back discount; an offer given after the counter's last catalog refresh (every 5 minutes online) is not known yet. Visits are sent as `visit.recorded` version 3, which adds `winBack`; a discount without a campaign is the offer's.
- **Checked again at sync.** Win-back lines must match the card's offer as it stood at the visit's time (given by then, and neither expired nor closed before it, within the campaigns' grace periods, and not used), giving exactly its own discount and keeping its floor. The visit uses the offer up, even when it is held for review (the customer had the discount); otherwise the visit is held for the owner like a refused campaign discount. Visit lines keep `win_back`.

## Feedback

- **When it is asked.** Every 15 minutes, for each café (`requestFeedback`, apps/worker/src/feedback.ts; the cafés come from `cafes_for_feedback`, migration 0015), each card's latest member visit (held, discarded and card-gone visits aside) gets a feedback request once it is 2 hours old, up to 24 hours (a card back within 2 hours waits for its newer visit), unless the card got one in the last 24 hours. The request puts a "How was your visit?" link on the card's Apple pass (a back field), Google pass (a links module) and web card, silently: AC 14's one notifying update a day is kept for offers.
- **The link** is `/f/<token>`: the café and request ids signed with the card QR keys under their own prefix (`signFeedbackToken`, packages/db/src/feedback.ts), so neither the server nor the worker stores it. A link that does not verify, or whose card was deleted, is not found.
- **The page** offers every customer both a private message to the owner (up to 2,000 characters, one per visit) and the café's Google review link. No rating is asked, so nothing decides who sees the review link (no review gating). It has the card pages' protections (no-store, no-referrer, noindex, no scripts) and is rate-limited per address.
- **The owner** sets the review link on the Café page (`PATCH /api/cafe` with `googleReviewUrl`: a Google review link only: a g.page short link, search.google.com/local/writereview, a maps.app.goo.gl link or a Maps place on google.com, never another Google page such as its /url or /amp/s/ redirectors; empty removes it) and reads messages in the Inbox (`GET /api/feedback`, the newest 200 with the unread count; `POST /api/feedback/:id/read`). Messages are anonymous, and the inbox shows only the hour of the visit they are about.
- **Deletion.** Requests and messages go with their card (foreign key cascades, AC 9).

## Results and plans

- **First-month results** (Results page, `GET /api/results`, owner only, AC 38): the 30 days from the café's first member visit (a visit not held or discarded), still running until they end. It shows member visits, customers won back (lapsed cards, see Win-back offers, that came back with a member visit), quiet-hour visits with a campaign discount, rewards redeemed, and each kind of offer's cost (its lines' discounts) against its revenue (the totals of the visits that had it).
- **Operators** run the service. `create-operator` makes an operator account; the operator signs in at `/admin` on the dashboard, with its own cookie (`__Host-cl_operator`, 2 hours idle, 12 hours at most), rate-limited like owner sign-in. Operator routes (`/api/admin/…`) answer 403 to owner sessions and device tokens, and owner routes ignore an operator's cookie. Operators and their sessions belong to no café: they are found with `withLookup` (email or session hash) and changed with `withOperator`.
- **Admin pages**: `/admin` lists the cafés (each a link to `/admin/cafes/<id>`, its signup links, plan and payments) with a New café link (`/admin/cafes/new`); the top bar's profile menu has Change password (`/admin/password`, `POST /api/admin/password`: the current password and a new one of at least 10 characters, rate-limited per operator, ending every session of the operator) and Sign out. The owner dashboard's top bar has the same menu, with Account and Sign out.
- **Cafés and signup links**: the admin screen creates a café on the pilot plan (`POST /api/admin/cafes`, with an id the form makes: sent again with the same name it answers with a fresh link, with another name 409) and makes a fresh owner signup link for any café (`POST /api/admin/cafes/:id/invites`). The link is in that response only (the server keeps its hash); creating the café and each link go in the café's audit log with the operator as actor.
- **Plans and payments** (AC 39): the admin screen lists every café (ids from `cafes_for_operator`, migration 0016, each café then read in its own `withCafe`), sets its plan (pilot, active or suspended) and records the payments it made by hand (amount, day, cash, Whish, OMT, bank transfer or other, an optional receipt or transfer number). Both go in the café's audit log with the operator as actor. A suspended café's signup page enrols no one (403 with a notice in Arabic and English); its counter still records and syncs visits and rewards, and its owner sees a notice on the home page.

## Customer cards

- **Signup.** The owner prints the café's signup QR (dashboard, Café page), which opens `PUBLIC_URL/join/<code>`. The customer enters a mobile number (Arabic-Indic digits, spaces, dashes, a leading `0` or `00961` are all fine; it is normalised to E.164), accepts the privacy notice and may opt in to offers; both are stored with their time. The reply is a redirect to a new web card, after at least 400 ms, whatever the number's history: a new number gets a linked card; a number known at other cafés gets a linked card here; a number that already has a card here gets a fresh, unlinked card that works by QR only, and the number can no longer stamp the existing card (see Stamping). The existing card is never shown. Signup is limited to 60 attempts per hour per address and, as a backstop, 1,000 cards per hour per café (valid signups only, so junk cannot shut a café's page); the owner can replace a misused code. Deleting a card also takes a minimum time, so it never reveals whether the card was linked.
- **Phone numbers** are stored as an HMAC-SHA256 lookup hash (`PHONE_LOOKUP_PEPPER`) and AES-256-GCM ciphertext (`PHONE_ENCRYPTION_KEYS`). A café reaches a customer only through its own cards. Because numbers are not verified, everything a card holder controls (recovery email, offers, deletion) belongs to the card, not the number.
- **Web card** (`/c/<256-bit secret>`): server-rendered in Arabic or English, with no script, a hash-based Content-Security-Policy, `no-store`, `no-referrer` and `noindex`. It shows the card itself (the café on an espresso face, the stamps as a grid of the program's slots with the stamps left, and the QR, signed with HMAC-SHA256 over card, café, epoch and key id (`CARD_QR_KEYS`), checked in constant time), then the offer the card holds when it is opted in to offers, the wallet button and the card's settings.
- **Recovery.** A card holder may add an email. `/recover` emails a single-use link (`/r/<token>`, 30 minutes, newest only, same reply whether or not a card uses the email). Opening it shows buttons; restoring gives every card with that email a new epoch and a new link, so old QR codes and links stop working and the old Apple pass is pushed voided, and deleting removes those cards.
- **Deletion.** Deleting a card (from its page, or all cards of an email from a recovery link) removes it with its Apple and Google passes and the Apple device registrations, and the phone number too once no café has a card for it. Deletions are audit-logged without personal data.

## Apple Wallet

- **Passes.** With the `APPLE_*` variables set, the web card on an Apple device (iPhone, iPad, Mac) offers "Add to Apple Wallet" (`/c/<secret>/apple-pass`): a signed store card in Arabic and English (Wallet picks the phone's language) with the stamps, the reward and the card's QR. A card has one pass per epoch, whose serial number is its row in `apple_passes`; downloading again gives the same pass. Its `authenticationToken` is an HMAC (with the pepper) of the web card's secret, 256 bits, stored only as its SHA-256. Sharing is off. Updates are silent: only the offer field may have a change message, on the day an offer is announced (see Quiet-hour campaigns), so a card gets at most one lock-screen notification a day.
- **Web service** (`PUBLIC_URL/passkit/v1`, Apple's PassKit web service): registration (201 new, 200 known, 401 bad token; at most 10 devices per pass, the oldest dropped), unregistration, the passes of a device changed since a tag (204 when none) and the latest pass (304 when unchanged since `If-Modified-Since`). Tags are transaction ids: `lastUpdated` is the oldest transaction still running, so a change committed later is never missed; a tag ahead of the database's counter (given out before a restore from a dump, which restarts it) lists every pass. A pass of an earlier epoch is served voided. A pass built on another layout (`APPLE_PASS_LAYOUT_VERSION`, stored per pass) counts as changed, so every device of it fetches the new one. Wallet's error reports are logged.
- **Updates.** A database trigger marks a card's current pass changed whenever its stamps change, and the pass an epoch change replaced (recovery), so writes from any release reach the passes; a pass voided earlier is never touched again, so a lost phone hears nothing of later visits. The change's transaction (visit, accepted visit, reward, recovery) also queues an `apple-pass-update` job per marked pass (one waiting job per pass). The worker pushes Wallet's empty notification to each registered device over APNs (HTTP/2, pass type certificate, 10-second timeout), drops a registration APNs reports gone (410, or a bad token), and fails the job on any other error, a token for another topic included (a worker with the wrong pass type id), logged with its job and café, for pg-boss to retry from 30 seconds up to an hour apart. A stamp never waits for APNs. A worker without the Apple variables leaves these jobs queued for one that has them.

## Google Wallet

- **Passes.** With the `GOOGLE_WALLET_*` variables set, the web card on any other device offers Google's own "Add to Google Wallet" badge in the page's language (the brand guidelines allow no other; `apps/server/assets/google-wallet`, which a server image must include). Its link (`/c/<secret>/google-pass`, at most 20 an hour per card) records the card's Google pass for its epoch (`google_passes`), queues its write, and redirects to Google's save page with a JWT signed by the service account carrying the café's loyalty class and the card's loyalty object. Ids derive from the issuer, the café and the card at its epoch (`<issuer>.cafe-<cafe id>`, `<issuer>.card-<card id>-<epoch>`), so every write lands on the same class and object. The object shows the stamps (`4/9`), the reward and the card's QR, in Arabic and English (Google picks the phone's language); the class logo is served at `PUBLIC_URL/wallet/logo.png`. Updates are silent (no `notifyPreference`); only an offer's announcement adds a notifying message (see Quiet-hour campaigns).
- **Updates.** As for Apple, a trigger marks a card's Google pass changed with its stamps, and the replaced one on recovery; the change's transaction queues a `google-pass-update` job per marked pass. The worker signs in as the service account (OAuth, token kept until near expiry) and replaces the whole object as the card now is (10-second timeout per request): the current epoch's object is created, with its class, when nobody saved it yet, so saving later finds it current; an earlier epoch's is written INACTIVE, without the QR, only if it exists. Errors keep Google's status only, never its answer, which could echo the QR.
- **Failures and catching up.** Every pass records its failed updates in a row (count, time, a short code such as `apns_503`, `google_503_UNAVAILABLE` or `ECONNREFUSED`), cleared by the next success, and the change its last successful update delivered (`delivered_xid`). Every 15 minutes the worker queues again each pass whose latest change was never delivered (`undelivered_passes`, oldest first, 500 per wallet per run): a job that ran out of retries, or a change made while the server had no job queue or by an older release, still reaches the phones. The dashboard home warns the owner about each wallet with passes that failed 3 times or more in a row (`GET /api/cafe/wallet-deliveries`) until they go through; every failure is also logged with its job and café.
- **Manual check (staging, real phones).** With both wallets configured on staging: run `wallet-check issue --cafe-id <a test café>`, open the link on an iPhone and an Android phone and add the card to each wallet; run `wallet-check stamp <link>` and check both passes show the new stamps within a minute without a notification; make a campaign on the dashboard, run `wallet-check offer <link>` and check each phone shows one notification of the new offer and the pass shows it, then run `stamp` again and check no second notification comes; end the campaign and check the offer leaves both passes within a minute, silently; run `wallet-check restore <link>` and check the Apple pass shows "Card moved" without its QR and the Google pass goes to expired passes, then add the card again from the new link. Delete the demo card from its web card afterwards.

## Continuous integration

`.github/workflows/ci.yml` runs `pnpm test` on Ubuntu with the Node version from `.nvmrc`, a frozen lockfile, Playwright Chromium and a PostgreSQL 18 service container (trust authentication, reachable only from the job). It has read-only repository permissions, pins every action to a commit SHA, and uploads the Playwright report (with the screen specs' screenshots) after every run that was not cancelled. A second job runs `pnpm test:deploy` with `RUNNER_UBUNTU=26.04`, so the VPS scripts are tested on both Ubuntu releases provision.sh supports (26.04 has Rust coreutils, sudo-rs and newer curl). `.github/workflows/release.yml` releases each merge to `main` once CI has passed on it (see Deploying).

## Provisioning the VPS

`deploy/provision.sh` sets up one Ubuntu VPS (24.04 or 26.04 LTS, x86-64; it refuses other releases) for production and staging, and brings it back to that setup when run again; it is safe to rerun at any time, never replaces a secret it generated, and upgrades Docker each time (containers keep running through Docker upgrades and restarts: live-restore; a runtime fix in such an upgrade reaches them when the next deploy recreates them). A run that stops part way is finished by the next one: Docker restarts when its settings are newer than the running daemon, and Caddy always reloads its configuration and must hold ports 80 and 443 before the run reports done. Point the six domains in its settings at the VPS first (Caddy needs them to get certificates), make sure your own SSH key logs in as root or as a sudo user (it turns password logins off and refuses to run otherwise), then from your machine:

```sh
scp -r deploy root@<vps>:cafe-loyalty-deploy
ssh root@<vps>
cd cafe-loyalty-deploy && cp provision.conf.example provision.conf   # then set the deploy user, its key, the image repository, the domains and the backup settings
sudo bash -c 'set -a && . ./provision.conf && set +a && ./provision.sh'
```

It sets up:

- **Access.** A deploy user (`DEPLOY_USER`) for CI, whose only keys are `PRODUCTION_DEPLOY_SSH_PUBLIC_KEY` and `STAGING_DEPLOY_SSH_PUBLIC_KEY` (two different keys) under `restrict` (no terminal, forwarding or agent), each with the forced command `ssh-command.sh <environment>`, which runs only `deploy.sh` or `rollback.sh` for that key's environment (so the staging key cannot deploy to production), kept in `/etc/ssh/authorized_keys/<user>`, which only root can change (sshd ignores keys in that user's home, and the script never writes there), no password, not in the `sudo` or `docker` groups (both give root; the script refuses to run if it is), and sudo only for the scripts it installs in `/opt/cafe-loyalty/bin` (every `deploy/*.sh` but itself; only root can write there). It also installs `deploy/compose.yaml` as `/opt/cafe-loyalty/compose.yaml` and writes `/etc/cafe-loyalty/deploy.conf` (`IMAGE_REPOSITORY`) for the deploy scripts (see Deploying). SSH takes keys only; root may log in with a key. A configuration sshd refuses is taken back before the script stops.
- **Firewall.** ufw allows 22 (rate-limited: at most 6 connections in 30 seconds from one address), 80 and 443 (TCP, and UDP for HTTP/3) and nothing else; the script fails on any other rule, and before enabling the firewall if sshd listens on another port. Docker's published ports bypass ufw, so the Docker daemon binds them to 127.0.0.1 unless a Compose file names another address.
- **Docker and Compose** from Docker's apt repository, its signing key file checked to hold exactly one key, with Docker's published fingerprint. Container logs are rotated (20 MB, 5 files), Caddy's access logs too (20 MiB, 10 files, 30 days), and the journal is capped at 1 GB.
- **Caddy** from its official image, pinned by digest (`CADDY_IMAGE` in the script; bump it to upgrade), run as the Compose project `/opt/cafe-loyalty/edge` with host networking (so ufw applies to it), no capabilities but binding ports 80 and 443, its admin API on a socket inside its own volume rather than a local port, and only the app builds and its configuration mounted. Its configuration (`/etc/caddy/Caddyfile`, generated) has automatic TLS for each environment's three domains: the dashboard and the counter each serve their build from `/srv/cafe-loyalty/<environment>/web/<app>`, with `index.html` for every app path (`/`, `/pair`, `/admin`), `/api` proxied to the server, `/assets/` cached for good and everything else (`index.html`, the counter's `sw.js`) revalidated on every load; the public domain proxies everything to the server (customer pages, PassKit, assets). Production's server is on 127.0.0.1:3100 and staging's on 3200; the dashboard and counter send a strict Content-Security-Policy (`deploy/spa-csp.txt`: no inline script or style, `data:` images for the QR codes and `data:` fonts for the small font subsets the builds inline; the end-to-end tests fail on anything it refuses); staging's sites send `X-Robots-Tag: noindex`. Access logs (`/var/log/caddy/<environment>-<app>.log`) leave out cookies and `Authorization`, and mask every run of 16 or more URL-safe characters in the address, the `Referer` and a response's `Location` (the server's redirects to cards, feedback pages and Google save links), so card, recovery and feedback links (`/c/`, `/r/`, `/f/`) never reach them whole; Caddy's own log (in `docker compose -f /opt/cafe-loyalty/edge/compose.yaml logs caddy`, where a 502 during a restart logs the request) is masked the same way.
- **Each environment** in `/srv/cafe-loyalty/<environment>`: `.env` for Compose (its project name, `cafe-loyalty-<environment>`, which keeps its containers, network and database volume apart, and `PROXY_PORT`); `database.env` (the PostgreSQL superuser and the bootstrap and migrator settings) and `app.env` (the server's and worker's settings), both mode 0600 and owned by root, with every password, the phone pepper and the phone and QR keys generated on the VPS the first time and never replaced; `web/` for the app builds (the deploy keeps each release's in `web/releases/<commit>/` and links `web/dashboard` and `web/counter` to the running one's) and `backups/` (mode 0700). `database.env` holds what the bootstrap and migration containers read too (`LOG_LEVEL` included); if it is lost while `app.env` remains, or both are lost while the environment's database volume remains, the script refuses to make new passwords (they would no longer match the database) and asks for them from a backup. Each environment runs its own PostgreSQL container, reachable as `postgres` on its own Compose network only, because the `cl_owner` and `cl_app` roles are cluster-wide. The script fails if production and staging share any password, key or credential, and lists each environment's email settings still to fill in `app.env` (as root): `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD` and `EMAIL_FROM`, plus the optional Apple and Google Wallet credentials. The dashboard, counter and public addresses in `app.env` follow the domains of each run.
- **Updates.** Unattended upgrades install Ubuntu's security updates daily and reboot for a kernel update at 02:00 UTC; the clock is set to UTC.
- **Backups.** age and rclone, `/etc/cafe-loyalty/backup.conf` (mode 0600) from the age and remote settings, `/etc/cafe-loyalty/alert.curlrc` (mode 0600, so the address never shows in a process list) from `ALERT_URL`, and the timers `cafe-loyalty-backup@<environment>.timer` nightly at 01:30 UTC and `cafe-loyalty-restore-test@<environment>.timer` on the first of each month, running `backup.sh` and `restore-test.sh` from `/opt/cafe-loyalty/bin` (`systemctl list-timers 'cafe-loyalty-*'` lists them). Either one failing POSTs the failed unit's name to `ALERT_URL` (`cafe-loyalty-alert@.service`). See Backups.

The generated files are tested without a VPS: `provision.sh caddyfile` prints the Caddy configuration and `provision.sh env-files <dir>` writes a production `database.env` and `app.env` (both from the `*_DOMAIN` settings, no root needed), and `provision.sh units <dir>` writes the backup, restore test and alert units and `alert.curlrc` (from the backup settings), `provision.sh authorized-keys` prints the deploy user's `authorized_keys` and `provision.sh deploy-conf <dir>` writes `deploy.conf` (the deploy test uses both); `pnpm test:deploy` runs the first in Caddy and sends the alert the last ones define, and unit tests in `packages/db` and `apps/server` check the second against the bootstrap, migration and server settings schemas.

## Backups

`deploy/backup.sh <environment> [nightly|predeploy]` (nightly from its timer; the deploy script takes a `predeploy` one) dumps the environment's database with the PostgreSQL container's own tools, as the superuser (only a superuser reads past row-level security), into `/srv/cafe-loyalty/<environment>/backups/<UTC time>-<kind>/`: `roles.sql` (roles and memberships, no passwords) and `database.dump` (`pg_dump` custom format). That stays on the VPS unencrypted, like the database itself. The copy that leaves is one file, `<name>.tar.age`: the backup plus the environment's `app.env` and `database.env` (without its pepper and keys the data cannot be used), encrypted with age to `BACKUP_AGE_RECIPIENT` and copied with rclone to `BACKUP_REMOTE/<environment>/<kind>/`. The private key never comes to the VPS, so neither the VPS nor the remote can read a copy. Retention: the newest 7 nightly and 3 pre-deploy backups on the VPS; off-site, nightly copies for 35 days, pre-deploy copies for 14, and the nightly copy of the 1st of each month (also in `monthly/`) for 400. An environment never deployed (no Compose volume) is skipped.

`deploy/restore-test.sh <environment> [<name>]` restores a backup (the newest nightly when none is named; it must be under 48 hours old and its encrypted copy must be off-site) into a throwaway container of the environment's PostgreSQL image, without a network. It checks that migrations are recorded, every table in `app` has forced row-level security, `cl_app` has neither superuser nor BYPASSRLS and sees no café without one set, and prints each table's row count. The container is removed afterwards.

Setup, once:

1. On your own machine: `age-keygen -o cafe-loyalty-backups.key`. Keep that file off the VPS (in your password manager too): it is the only way to read the backups. Its public key (`age1…`) is `BACKUP_AGE_RECIPIENT`.
2. A bucket with another provider than the VPS (Backblaze B2, Cloudflare R2, any S3), and on the VPS `sudo rclone config --config /etc/cafe-loyalty/rclone.conf` to add it as a remote. `BACKUP_REMOTE` is `<remote>:<bucket or path>`; provision.sh reminds you while the remote is missing. For Cloudflare R2 (type `s3`, provider `Cloudflare`, a token limited to the bucket), add `no_head = true` to the remote: Ubuntu's rclone (1.60) checks each upload with a HEAD request carrying a version id, which R2 answers with 501, so every copy fails without it. The tradeoff: rclone no longer reads each copy back after the upload, and relies on the MD5 it sends with the upload, which R2 checks on receipt. `restore-test.sh` checks only that the copy is off-site (it restores the plain dump on the VPS), so to check an off-site copy itself, now and then fetch and decrypt one as in step 1 of Recovery below.
3. `ALERT_URL`: an https address taking a POST with a plain-text body, such as an ntfy.sh topic with a long random name (subscribe to it on your phone) or a healthchecks.io URL ending in `/fail`.

By hand, as root: `systemctl start cafe-loyalty-backup@production` (or `/opt/cafe-loyalty/bin/backup.sh production`), `/opt/cafe-loyalty/bin/restore-test.sh production [<name>]`, and `journalctl -u 'cafe-loyalty-*'` for their logs.

Recovery, when the database or the whole VPS is lost:

1. On your machine, fetch a copy (`rclone copy <remote>:<path>/production/nightly/<name>.tar.age .`) and unpack it: `age -d -i cafe-loyalty-backups.key <name>.tar.age | tar -xf -`, giving `<name>/`. If the VPS still has the backup in `backups/`, skip this.
2. On a new VPS, before running provision.sh: put `<name>/app.env` and `<name>/database.env` in `/srv/cafe-loyalty/<environment>/` (owned by root, mode 0600). provision.sh keeps them, so the database passwords, the pepper and the keys are the old ones. Put `<name>/` in that environment's `backups/`, then provision and deploy as usual.
3. Stop the environment's server and worker (`docker stop cafe-loyalty-production-server-1 cafe-loyalty-production-worker-1`), then replace the database with the backup (its roles exist from the deploy's bootstrap; `restore-test.sh <environment> <name>` first checks the backup):

```sh
pg=$(docker ps -q --filter label=com.docker.compose.project=cafe-loyalty-production --filter label=com.docker.compose.service=postgres)
docker exec "$pg" dropdb -U postgres --force cafe_loyalty
docker exec -i "$pg" pg_restore -U postgres --create --exit-on-error -d postgres </srv/cafe-loyalty/production/backups/<name>/database.dump
```

Then start them again: `docker start cafe-loyalty-production-server-1 cafe-loyalty-production-worker-1`. `pnpm test:deploy` runs both scripts and this recovery against a migrated database, and the generated alert against a local listener (`deploy/test/backup.sh`).

## Deploying

A release is one image, `<IMAGE_REPOSITORY>:<commit>` (the `Dockerfile`): the server, the worker, the database CLIs and the dashboard and counter builds, with the commit in `BUILD_ID` and its time in `BUILT_AT` (the server and the counter build agree on it, AC 26), the release's git history in `/app/release-commits.txt`, no npm, and no secret in any argument or layer: every setting comes from the environment's `app.env` and `database.env`. Each environment runs it as the Compose project in `/srv/cafe-loyalty/<environment>` from `/opt/cafe-loyalty/compose.yaml` (`deploy/compose.yaml`): `postgres` (the CI image, its data in the project's `pgdata` volume, no published port), `server` (on `127.0.0.1:<PROXY_PORT>`, healthy when `GET /health/ready` answers 200: the database and the job queue answer) and `worker`, read-only and without capabilities, and the one-off `bootstrap` and `migrate`.

On the VPS, as root (the release workflow runs them as the deploy user with sudo):

- `/opt/cafe-loyalty/bin/deploy.sh <environment> <commit> <digest>` pulls the image by digest (refusing one labelled with another commit, or a release that is not at or after the running one: going back is `rollback.sh`'s), takes the encrypted pre-deploy backup (`backup.sh <environment> predeploy`; it fails the deploy before anything changes), runs `bootstrap` and then `migrate` in one-off containers, restarts the server and worker on the release (the server is down for a few seconds; the script prints how long), waits up to 120 seconds for the server's readiness and 10 more for the worker to stay up, switches `web/dashboard` and `web/counter` to the release's builds (one rename each), and records the release in `/srv/cafe-loyalty/<environment>/releases.log`. A run goes on when the SSH session that started it ends (a job timeout or a cancel), and its output is also kept in `release-output.log` there. If the release does not get ready, it runs the previous recorded release again on the same schema (no migration is undone), records both and fails. It keeps the images and web builds of the last 5 releases of each environment.
- `/opt/cafe-loyalty/bin/rollback.sh <environment> [<commit>]` runs a recorded release again (the one before the current one when no commit is given) without touching the schema, the same way, going back to the current one if it does not get ready. It refuses a release from before a contract migration the database has (see below), and exits 3 when no other release ever ran.

Migrations at deploy time (AC 47, 52): `migrate` runs with `MIGRATE_MODE=expand` and the running release's commits on stdin. Expand migrations are applied; a contract migration only when the running release is at or after its `requires-deployed` commit, and otherwise the deploy is refused before any migration runs or anything restarts. So a contract change ships in two releases: first the one that stops using the column or table (merge and deploy it to both environments), then the contract migration naming that release's commit. The migration records that commit, and `rollback.sh` refuses releases from before it. The first deploy of an environment applies everything.

The release workflow (`.github/workflows/release.yml`, AC 48, 51, 54), on every push to `main` once CI has passed: builds the image from the commit with its full history, scans it with Trivy (secrets, and HIGH or CRITICAL vulnerabilities that have a fix; a finding stops the release before the push), pushes it to GHCR, deploys it to staging with `deploy/ci/remote.sh` (one SSH connection per script), runs the smoke tests (`deploy/ci/smoke.sh`: readiness through Caddy, both apps with their Content-Security-Policy and `/api`, the counter's `sw.js` revalidated and of this release), then the rollback test: staging runs the previous release on this release's schema, passes the smoke tests, and runs this release again. Production then deploys the same digest once the production environment's reviewers approve, and runs the smoke tests. A failed deploy fails its job with the script's output.

Setup, once:

1. `IMAGE_REPOSITORY` in provision.conf is `ghcr.io/<owner>/<repository>` (lowercase); run provision.sh again after adding it. The VPS pulls without credentials, so after the first release make the package public (the package's settings on GitHub, Change visibility); the image holds no secrets.
2. On GitHub, Settings, Environments: `staging`, and `production` with required reviewers (you). Limit both to the `main` branch (Deployment branches and tags). On each environment, the variables `DEPLOY_HOST` (the VPS's address), `DEPLOY_USER` (provision.conf's), `PUBLIC_URL`, `DASHBOARD_URL` and `COUNTER_URL` (that environment's `https://` addresses), and the secrets `DEPLOY_SSH_KEY` (the private key of that environment's `*_DEPLOY_SSH_PUBLIC_KEY`; environment secrets only, never repository secrets, so only an approved production job holds the production key) and `DEPLOY_KNOWN_HOSTS` (the VPS's host key line: `ssh-keyscan -t ed25519 <vps>`, checked against `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the VPS).

One-off commands on the VPS (as root), in a throwaway container of the running release, so their output stays out of container logs:

```sh
env=production
image=$(docker inspect --format '{{.Config.Image}}' cafe-loyalty-$env-server-1)
APP_IMAGE=$image docker compose --project-directory /srv/cafe-loyalty/$env -f /opt/cafe-loyalty/compose.yaml run --rm --no-deps server node apps/server/dist/create-invite-cli.js --cafe-name "<name>"
```

Releasing a counter change: every pull request that changes the counter freezes that counter build's sync fixture (`freeze-sync-fixture <name>`, see Commands) before it merges, so the contract test keeps replaying what each released counter sends for the support window.

`pnpm test:deploy` builds the release image from the checkout and runs both scripts as root in an Ubuntu 24.04 container (26.04 with `RUNNER_UBUNTU=26.04`, as CI's second job runs them), with the real Compose file and generated environment files, against a local registry, with the deploy keys and `deploy.conf` provision.sh generates and `deploy/ci/remote.sh` going through a stand-in `ssh` that applies the keys' forced commands (`deploy/test/deploy.sh`): the keys (each runs only its environment's scripts), the first deploy, a deploy adding an expand migration (backup, migration, downtime under 30 seconds, web switch), a release whose server never gets ready (the web builds unchanged while it is waited for, fallback, nothing undone) and one whose worker stops, a redeploy of the running release after a worker restart whose session ends at once, rollbacks to the previous and a chosen release on the expanded schema (the older server answering API requests) and to one that does not get ready, pruning past five releases (web builds and images), both contract gates and the argument checks.

## Configuration

Every setting comes from environment variables; `.env.example` lists all of them, with optional ones commented out at their defaults. Each app validates its environment at start-up and exits with the names of any missing or invalid variables, never their values. `BUILT_AT` (the release's commit time, ISO 8601 UTC) must be the same for the server and the counter build of a release; CI sets it from the commit, and the server requires it in production.
